日期：2026-09-08。当前完成协议请求、快照准备、原生数据库检查点、详情事务落库、分批流扫描和会话队列消费确认。登录/重连协调器尚未接线；**App 尚未启用 V2，也未生成支持 V2 的 Android/iOS 二进制**。后续开发、编译和 App 依赖接入均在本地 worktree 完成，不推送 GitHub。

## 已实现与验证

- 五类 HTTP 请求保留 token/operationID 鉴权头、服务端错误码及原因；不记录凭据或消息载荷。默认请求超时 70 秒，覆盖服务端 60 秒快照构建窗口；调用方上下文可提前取消。
- 请求采用后端 `a2r` 实际使用的 Go JSON 编码，避免 Protobuf JSON 把 int64 序号编码成字符串后导致服务端绑定失败。业务 ID 始终为字符串，序号使用 Go int64 保持精度。
- 只有明确的能力响应才能选择协议；空响应、HTTP 404、Redis 故障不进入旧协议。
- chat/notifications 复用一个快照，分别分页。元数据、游标和完整性校验失败不发布半份集合。取消时仍尝试释放；释放失败通过诊断字段返回，TTL 兜底，不导致已完整读取的快照重建。
- 状态请求按协商数量/字节上限分批，仅对明确的容量错误缩批；空聊天请求跳过；自通知单独请求一次。
- 准备阶段保留设备已加载会话，错误分类不执行删除、无限重试或自动降级。
- 独立 SQLite 检查点表保存策略、阶段、选择集合、通知集合和快照基准版本。现有数据库也执行迁移，不覆盖旧 `LocalVersionSync.UIDList`。快照未完整读取时重建；完整读取后允许详情/消息阶段幂等重放。
- `PrepareRound` 最多写到 `details` 阶段，不能代表详情、消息落库或同步完成。
- `PrepareDetails` 已串起 HTTP→SQLite：会话详情 upsert 与推进到 `messages` 阶段在同一事务中提交；任一条失败时全部回滚。仅更新服务端字段，保留草稿、历史和展示信息；state 的有效边界优先于 detail 原始边界。未知/缺失状态、无权限 ID 分开持久化，不能据此删除本地记录。
- 本地 generation 区分同步轮次，旧快照晚返回不能覆盖新检查点；详情落库同时核对 generation、snapshotID 和基准版本。本地 generation 不代替服务端 stateToken，也不等于已实现清空/权限事件的在途失效。
- `PullBatched` 按数量/字节限制分批，仅对明确容量错误缩批，保留 unresolvedSeqs；校验响应流和 stateToken，不返回部分过期结果。通知父 ID 按固定服务端实现映射到通知流（例如 `sg_parent` → `n_parent`），请求仍携带父 ID。
- 新增独立流进度表：真实消息与扫描游标、未解决序号在同一事务保存；重启后缺口仍可重试，补齐后移除。扫描游标不等于历史完整性。消息 upsert 补齐本地发送的服务端序号，并保留本地已读、删除状态和扩展信息。
- 每个流保存本地 epoch。状态查询前捕获 epoch，接纳新的 stateToken 时递增，事件失效也递增；过期的消息响应和详情响应均不能落库。详情阶段在 HTTP 读取前批量捕获流 epoch，事务内再比较。事件入口尚待接入，不能把数据库层用例当作完整事件链已验证。
- 通知进度单独提交，旧 NotificationSeqs 游标停在最早未解决缺口之前。好友、群、用户、会话通知处理器现已返回错误，供 V2 消费者在成功处理后提交进度；旧调用方保留原有行为。
- 合成 5 万会话用例验证只请求 150 个选中聊天的详情，仍遍历全部通知父 ID；这不是大账号真机性能验收。

### 本地推进：流扫描与消费确认

- `SyncStream` 按当前权限边界逐批扫描，每轮对已有缺口只重试一次；新缺口保存到下一轮。返回结果缺少请求序号、重复序号或流令牌不一致时拒绝推进游标。
- `SyncStreams` 分批读取状态，并在每批 HTTP 请求前捕获 epoch。合成 50,000 个通知父会话及自通知的测试只产生 101 次状态请求，不为每个会话单发请求；这是请求规模测试，不是大账号真实耗时测量。
- 第一次接纳通知流状态时，在同一事务继承旧 `NotificationSeqs` 游标；即使此前已有失效记录也可继承。后续不再从旧游标覆盖 V2 进度，避免重新消费旧通知或跳过新任务。
- `ConsumeConversationSyncV2` 在现有 Conversation 串行队列内消费，消息用现有历史转换方式保留内容、组接收 ID 和服务端明确的删除状态。落库成功才返回确认；通知处理失败不提交游标，已取消或失效的排队响应不能继续落库。
- `MsgSyncer` 的连接、唤醒和手动同步入口已有 V2 协调器钩子；钩子返回错误时不能进入旧 WS 流程。**当前尚未安装该钩子，不能把入口单元测试视为生产链路已启用。**
- 当前消费者只负责消息/通知持久化确认；会话最新消息投影、头像名称补齐、UI 回调、事件失效调用和完整轮次成功回调仍需统一接入。

### 本地推进：元数据增量合并

- `PlanMetadataDelta` 保留已有加载集合，普通资料更新不创建展示会话；置顶可激活。新增/变更父会话继续加入独立通知集合，显式删除遵循旧增量协议的删除优先语义。
- `ApplyMetadataDelta` 即使元数据版本没有增长，也重新查询选中会话的 V2 有效详情与边界。服务端要求 `full`、版本标识改变或版本回退时返回重建 V2 快照信号，不调用旧全量路径。
- 元数据版本、选中详情、显式删除和删除流的失效记录同事务提交。只删除会话记录，不删除历史消息表；故障注入验证检查点写失败时数据一起回滚。
- 新增本地 `Revision` 防止服务端元数据版本未变化时，晚返回的旧详情覆盖新边界。旧修订的检查点写入和详情合并均被拒绝。
- 已完成 HTTP→SQLite 的元数据增量测试；调用方仍需在运行协调器中串起元数据接口、通知消费和消息追赶，不能据此报告 App 运行链路已完成。

### 本地推进：协调流程与 WS 边界

- `Client.Synchronize` 串起快照/详情、相关数据准备、通知消费、元数据合并、聊天消息追赶和展示投影；投影完成及检查点成功写入后才返回 `ready`。它尚未接入 `LoginMgr`，运行时的准备/展示钩子和模式注册仍待完成。
- 至少进行两轮通知/元数据/消息追赶；增量中新出现通知父会话时继续读取，最多三轮，仍持续变化则返回可退避重试结果，不伪报完成，也不无限即时循环。
- 集成测试通过真实 Conversation 串行队列和 SQLite 验证：同一元数据版本下新增消息得到补拉；消费者失败不进入 ready；末轮新增通知父会话不会跳过；持续新增父会话时有界退出。
- `LongConnMgr.SetSyncRequestGuard` 提供发送前的同步请求检查点，测试覆盖全量序号、全量已读、范围拉取、指定序号拉取和最新消息五个旧入口。当前尚未注册运行模式守卫，不能声称这些旧路径已经在 App 中被替换。
