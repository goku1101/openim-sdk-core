## 已实现与验证

- 五类 HTTP 请求保留 token/operationID 鉴权头、服务端错误码及原因；不记录凭据或消息载荷。默认请求超时 70 秒，覆盖服务端 60 秒快照构建窗口；调用方上下文可提前取消。
- 请求采用后端 `a2r` 实际使用的 Go JSON 编码，避免 Protobuf JSON 把 int64 序号编码成字符串后导致服务端绑定失败。业务 ID 始终为字符串，序号使用 Go int64 保持精度。
- 只有明确的能力响应才能选择协议；空响应、HTTP 404、Redis 故障不进入旧协议。
- chat/notifications 复用一个快照，分别分页。元数据、游标和完整性校验失败不发布半份集合。取消时仍尝试释放；释放失败通过诊断字段返回，TTL 兜底，不导致已完整读取的快照重建。
- 状态请求按协商数量/字节上限分批，仅对明确的容量错误缩批；空聊天请求跳过；自通知单独请求一次。
- 准备阶段保留设备已加载会话，错误分类不执行删除、无限重试或自动降级。
- 独立 SQLite 检查点表保存策略、阶段、选择集合、通知集合和快照基准版本。现有数据库也执行迁移，不覆盖旧 `LocalVersionSync.UIDList`。快照未完整读取时重建；完整读取后允许详情/消息阶段幂等重放。
- `PrepareRound` 最多写到 `details` 阶段，不能代表详情、消息落库或同步完成。
- `PrepareDetails` 已串起 HTTP→SQLite：会话详情 upsert 与推进到 `messages` 阶段在同一事务中提交；任一条失败时全部回滚。仅更新服务端字段，保留草稿、历史和展示信息；state 的有效边界优先于 detail 原始边界。未知/缺失状态、无权限 ID 分开持久化，不能据此删除本地记录。
- 本地 generation 区分同步轮次，旧快照晚返回不能覆盖新检查点；详情落库同时核对 generation、snapshotID 和基准版本。本地 generation 不代替服务端 stateToken，也不等于已实现清空/权限事件的在途失效。
- `PullBatched` 按数量/字节限制分批，仅对明确容量错误缩批，保留 unresolvedSeqs；校验响应流和 stateToken，不返回部分过期结果。通知父 ID 按固定服务端实现映射到通知流（例如 `sg_parent` → `n_parent`），请求仍携带父 ID。
- 新增独立流进度表：真实消息与扫描游标、未解决序号在同一事务保存；重启后缺口仍可重试，补齐后移除。扫描游标不等于历史完整性。消息 upsert 补齐本地发送的服务端序号，并保留本地已读、删除状态和扩展信息。
- 每个流保存本地 epoch。状态查询前捕获 epoch，接纳新的 stateToken 时递增，事件失效也递增；过期的消息响应和详情响应均不能落库。详情阶段在 HTTP 读取前批量捕获流 epoch，事务内再比较。事件入口尚待接入，不能把数据库层用例当作完整事件链已验证。
- 通知进度单独提交，旧 NotificationSeqs 游标停在最早未解决缺口之前。好友、群、用户、会话通知处理器现已返回错误，供 V2 消费者在成功处理后提交进度；旧调用方保留原有行为。
- 合成 5 万会话用例验证只请求 150 个选中聊天的详情，仍遍历全部通知父 ID；这不是大账号真机性能验收。

### 本地推进：流扫描与消费确认

- `SyncStream` 按当前权限边界逐批扫描，每轮对已有缺口只重试一次；新缺口保存到下一轮。返回结果缺少请求序号、重复序号或流令牌不一致时拒绝推进游标。
- `SyncStreams` 分批读取状态，并在每批 HTTP 请求前捕获 epoch。合成 50,000 个通知父会话及自通知的测试只产生 101 次状态请求，不为每个会话单发请求；这是请求规模测试，不是大账号真实耗时测量。
- 第一次接纳通知流状态时，在同一事务继承旧 `NotificationSeqs` 游标；即使此前已有失效记录也可继承。后续不再从旧游标覆盖 V2 进度，避免重新消费旧通知或跳过新任务。
- `ConsumeConversationSyncV2` 在现有 Conversation 串行队列内消费，消息用现有历史转换方式保留内容、组接收 ID 和服务端明确的删除状态。落库成功才返回确认；通知处理失败不提交游标，已取消或失效的排队响应不能继续落库。
- `MsgSyncer` 的连接、唤醒和手动同步入口已有 V2 协调器钩子；钩子返回错误时不能进入旧 WS 流程。该钩子已在本地 `LoginMgr.login` 注册；App 仍使用旧二进制，尚未启用这些源码。
- 消费者负责消息/通知持久化确认；本地运行适配已加入最新消息投影、头像名称补齐和完整轮次回调，事件失效及历史/推送替换仍待完成。

### 本地推进：元数据增量合并

- `PlanMetadataDelta` 保留已有加载集合，普通资料更新不创建展示会话；置顶可激活。新增/变更父会话继续加入独立通知集合，显式删除遵循旧增量协议的删除优先语义。
- `ApplyMetadataDelta` 即使元数据版本没有增长，也重新查询选中会话的 V2 有效详情与边界。服务端要求 `full`、版本标识改变或版本回退时返回重建 V2 快照信号，不调用旧全量路径。
- 元数据版本、选中详情、显式删除和删除流的失效记录同事务提交。只删除会话记录，不删除历史消息表；故障注入验证检查点写失败时数据一起回滚。
- 新增本地 `Revision` 防止服务端元数据版本未变化时，晚返回的旧详情覆盖新边界。旧修订的检查点写入和详情合并均被拒绝。
- 已完成 HTTP→SQLite 的元数据增量测试；本地协调器已串起元数据接口、通知消费和消息追赶；不能据此报告 App 运行链路已验收。

### 本地推进：协调流程与 WS 边界

- `Client.Synchronize` 串起快照/详情、相关数据准备、通知消费、元数据合并、聊天消息追赶和展示投影；投影完成及检查点成功写入后才返回 `ready`。现已通过运行适配接入 `LoginMgr`，仍需完成其余消息入口的 V2 替换。
- 至少进行两轮通知/元数据/消息追赶；增量中新出现通知父会话时继续读取，最多三轮，仍持续变化则返回可退避重试结果，不伪报完成，也不无限即时循环。
- 集成测试通过真实 Conversation 串行队列和 SQLite 验证：同一元数据版本下新增消息得到补拉；消费者失败不进入 ready；末轮新增通知父会话不会跳过；持续新增父会话时有界退出。
- `LongConnMgr.SetSyncRequestGuard` 提供发送前的同步请求检查点，测试覆盖全量序号、全量已读、范围拉取、指定序号拉取和最新消息五个旧入口。守卫已注册到本地运行适配；目前历史/最新消息旧 WS 会被拦截，对应 V2 查询和激活入口尚未完成，暂不可提测。

### 本地推进：按序号历史补拉

- 历史缺口入口改用 V2 状态查询和按序号读取；请求按有效边界裁剪、去重，真实消息、边界、未读和缺口进度在消费队列内同事务提交。任意历史页不推进后台顺序扫描游标，不制造删除占位。

### 本地推进：在线推送分流与可靠回调

- `PlanPush` 将持久化聊天、独立通知和 seq=0 即时事件分开。有效聊天消息可成为激活候选；明确不更新会话、仅发送者不更新、删除消息及输入状态不恢复被延后的聊天。已加载会话仍参与状态追赶。
- 通知不受聊天选择集合限制；父 ID 从检查点通知集合映射，自通知使用独立请求。未知或映射有歧义的通知流单独返回，不能猜测聊天前缀。含下划线 ID 的用例已覆盖。
- `consumeConversationSyncV2Live` 通过现有消费队列先持久化，再发单条或批量接收回调。已存消息（含本机发送确认）不重复通知，删除/不更新会话消息不发接收回调，权威未读数不在此重复递增；旧 epoch 不落库、不回调。
- `MsgSyncer.SetConversationSyncV2Push` 增加受控推送处理钩子，成功接管或处理出错均不能落回旧序号比较/WS 补拉。仅明确未接管且没有错误时保留 legacy。上述行为有独立和真实 SQLite/Conversation 队列测试。
- **尚未注册运行适配：** 本节钩子仍需连接分流、V2 状态/消息追赶、详情/展示刷新和即时事件处理；未知父会话需有界重建/重试。新激活聊天补历史时，接收回调不能把全部旧历史当作刚到的新消息。当前不能报告线上推送已切换，也未做 App 模拟器验收。

### 本地推进：推送运行适配已注册

- `LoginMgr` 现在注册 `ProcessConversationSyncV2Push`。适配串起即时事件、通知流追赶、聊天详情刷新、消息持久化、目标会话展示及回调；与完整同步共用运行锁，但消费队列内不再次等待该锁。
- 新激活会话允许补齐当前权限内历史，但接收回调只包含本次推送中的消息；同一处理的冲突重试保留此限制，重复投递不重复回调。已有会话按持久化进度追赶，未读从服务端状态取值。
- 先消费独立通知，再处理聊天。延后会话通知和自通知均持久化游标，seq=0 通知即时分发不推进游标。通知处理与消费确认复用同一错误返回逻辑。
- 未知通知父 ID、服务端要求重建或重新协商时，退出推送运行锁后调用完整 V2 同步，再重试一次。版本冲突/可重试错误有一次延迟重试；最终失败不能转旧 WS。单会话 unavailable/unknown 不阻止同批其他有效聊天继续处理，但整体返回待确认状态。
- 真实 HTTP→SQLite→Conversation 队列测试覆盖新会话恢复、历史落库但只通知新消息、展示更新、重复推送、延后通知、自通知、即时通知、部分无权限、未知父 ID 重建失败；协议/原生范围竞态回归与 SDK 编译通过。尚无真实 WSS 或双端 App 运行证据。
- 剩余：持久化缺口/失败推送的后台退避重试，初次激活与初次同步的历史窗口成本控制，权限通知失效完整链，以及新原生产物接入 App。不能把本节注册和集成测试等同于模拟器验收。

### 本地推进：初始化聊天窗口和分页开销

- 原生完整同步通过调用级 `WithChatWindow` 限制聊天新增扫描范围：新安装 1 条，已有设备恢复 10 条，使用旧 SDK 已有的消息预算值。该值不进入服务端协议，也不会改变历史按需查询；调用未指定窗口时仍按其流范围处理。
- 通知流不截断。已持久化 pending 序号优先重试，即使它位于聊天尾部窗口之外；只有新扫描部分应用窗口。跳过的旧聊天历史不写删除占位，扫描游标不代表所有历史已下载。
- 真实 HTTP/SQLite 的百万序号用例验证初次只请求尾部 1 条、恢复只请求尾部 10 条并额外补旧缺口；通知用例仍消费整个允许范围。失败消费不推进游标仍由既有测试覆盖。
- `getLostSeqListWithLimitLength` 按目标方向最多收集一个批次，再保持原有升序输出，避免历史分页先分配整个巨大序号区间。正反向、已有序号排除、倒置范围和 MaxInt64 边界测试通过。
- 在线推送的新会话激活尚未使用这个完整同步窗口；需结合本次推送的具体序号保留接收行为，不能机械截断而丢失推送消息。大账号真实流量及 App 双端验收仍未完成。

### 本地推进：群权限事件失效

- 群模块提供登录前配置的失效回调，由 Conversation 原生运行适配检查协商模式并映射 `sg_` 聊天 ID，不更改独立 `n_` 通知流。业务群 ID 始终保留原始字符串。
- 本人退群、本人被踢和群解散通知在后续群同步前失效旧聊天请求。主动退群/解散（以及踢人列表包含本人）的接口仅在服务端成功后失效；离线群增量明确删除成员所属群记录时也失效。
- 测试覆盖三种通知先失效并传播错误；真实 HTTP/SQLite 测试证明退群成功而后续群刷新失败时，旧请求仍不能写回，草稿不被清除，通知游标不受影响。接口本身失败、明确 legacy、其他成员退群/被踢均不修改当前用户的聊天 epoch。
- **仍需补齐缓存读取边界：** 完全命中本地缓存的历史页可能不经过 V2 状态查询，应在权限失效后先刷新状态并在本地查询应用有效边界；不能仅凭本节在途保护报告完整权限验收。真实退群/被踢/解散的 App 场景尚未验收。

### 本地推进：缓存历史页权限检查

- V2 历史入口遇到未初始化或已失效流时，先读取当前状态并通过消费队列提交边界；无需消息补拉时不请求消息接口。仍有效的已确认缓存状态可复用。

- 递归补页结束后再次检查权限并过滤返回列表，避免请求过程中发生失效而继续暴露缓存记录。unknown/unavailable/missing 详情响应现在也使旧状态令牌失效，不能继续复用此前已确认边界。
